# RetroMarket — Apresentação Didática dos Diagramas de Atividades

## 1. Objetivo

Este material apresenta os **Diagramas de Atividades do projeto RetroMarket**, uma plataforma de anúncios de videogames retrô.

Os diagramas foram construídos a partir dos requisitos funcionais, histórias de usuário, casos de uso e modelo conceitual de domínio definidos para o projeto.

O objetivo é compreender:

- o que é um Diagrama de Atividades;
- para que ele é utilizado;
- como identificar um processo a partir dos requisitos;
- como representar ações, decisões, caminhos alternativos e repetições;
- como utilizar raias para distinguir responsabilidades;
- como os diagramas se relacionam com os demais artefatos de análise e projeto.

---

# 2. O que é um Diagrama de Atividades?

O **Diagrama de Atividades** é um diagrama comportamental da UML utilizado para representar o fluxo de um processo.

Enquanto o modelo de domínio descreve principalmente **os conceitos existentes no problema e seus relacionamentos**, o Diagrama de Atividades representa **o que acontece durante a execução de um processo**.

De forma simplificada:

```text
Modelo de domínio
    ↓
Quais conceitos existem?
    ↓
Diagrama de atividades
    ↓
O que acontece e em que sequência?
```

No RetroMarket, `Anúncio` é um conceito do domínio. Já o processo:

```text
Preencher dados
      ↓
Validar
      ↓
Criar anúncio
      ↓
Publicar
```

representa comportamento e pode ser modelado por um Diagrama de Atividades.

---

# 3. Por que utilizar Diagramas de Atividades no RetroMarket?

O projeto possui processos com diferentes caminhos possíveis.

Ao publicar um anúncio:

- os dados precisam ser informados;
- os dados precisam ser validados;
- podem existir fotos;
- erros podem exigir correção;
- o anúncio pode ser publicado após a validação.

Na pesquisa:

- o usuário pode pesquisar ou simplesmente consultar;
- pode utilizar filtros;
- pode ordenar os resultados;
- pode não encontrar resultados;
- pode refinar a busca.

No gerenciamento:

- o usuário pode editar;
- gerenciar fotos;
- alterar o status;
- retirar o anúncio;
- o sistema precisa verificar se ele é o proprietário.

Os diagramas tornam esses comportamentos explícitos.

---

# 4. Como um requisito é transformado em uma atividade?

O ponto de partida não é o diagrama, mas os **requisitos e histórias de usuário**.

Considere:

> Como usuário, quero publicar um anúncio de um produto retrô para disponibilizá-lo para outros usuários.

Podemos perguntar:

**O que o usuário precisa fazer?**

```text
Informar dados
Adicionar informações do produto
Adicionar fotos
Confirmar publicação
```

**O que o sistema precisa fazer?**

```text
Validar dados
Criar anúncio
Definir estado inicial
Registrar informações
Confirmar publicação
```

Essas ações podem então ser organizadas em um fluxo.

```text
História de usuário
       ↓
Identificação das ações
       ↓
Identificação das decisões
       ↓
Identificação dos caminhos alternativos
       ↓
Organização da sequência
       ↓
Diagrama de Atividades
```

# 5. Elementos fundamentais

## 5.1 Estado inicial

Representa o início do processo.

```text
●
```

## 5.2 Atividade/Ação

Representa uma ação realizada durante o processo.

Exemplos:

```text
Informar dados do anúncio
Validar dados
Criar anúncio
Consultar anúncios
Selecionar filtros
```

Normalmente é representada por um retângulo com cantos arredondados.

## 5.3 Fluxo

As setas indicam a sequência:

```text
Informar dados
      ↓
Validar dados
      ↓
Criar anúncio
```

## 5.4 Decisão

Representa um ponto em que o fluxo pode seguir caminhos diferentes.

```text
       ◇
      /     Não  Sim
```

Exemplo:

```text
Dados válidos?
   /        Não       Sim
```

## 5.5 Caminhos alternativos

```text
Dados válidos?
    │
 ┌──┴──┐
Não   Sim
 │     │
 ▼     ▼
Erro  Continuar
```

## 5.6 Repetição

Um fluxo pode retornar a uma atividade anterior:

```text
Informar dados
      ↓
Validar
      ↓
Dados válidos?
   Não ↓
      └──────────► Informar dados
```

Esse mecanismo é útil para representar correção de erros e refinamento de pesquisas.

# 6. Uso de raias (Swimlanes)

Os diagramas do RetroMarket utilizam **raias** para separar responsabilidades:

```text
┌─────────────────────┬──────────────────────┐
│       USUÁRIO       │       SISTEMA        │
└─────────────────────┴──────────────────────┘
```

### Usuário

Executa ações como:

- informar dados;
- selecionar filtros;
- escolher uma operação;
- adicionar fotos;
- corrigir informações.

### Sistema

Executa ações como:

- validar;
- consultar;
- verificar propriedade;
- salvar;
- atualizar;
- apresentar resultados.

As raias ajudam a introduzir o conceito de **responsabilidade**, que será aprofundado posteriormente na arquitetura.

# 7. DA01 — Publicar anúncio

## Objetivo

Representar o processo de criação e publicação de um anúncio.

Relaciona-se principalmente aos requisitos de:

- cadastro de anúncios;
- definição das características do item;
- associação à plataforma e categoria;
- inclusão de fotos;
- validação;
- publicação.

## Pré-condição

O processo parte da condição:

> **Usuário autenticado.**

O login não foi colocado dentro do DA01 porque autenticação é um processo próprio.

```text
Autenticação
     ↓
Usuário autenticado
     ↓
Publicar anúncio
```

## Fluxo principal

```text
Início
  ↓
Informar dados
  ↓
Validar dados
  ↓
Dados válidos?
  ├── Não → Corrigir dados
  │             ↓
  │         Validar novamente
  │
  └── Sim
        ↓
   Adicionar fotos?
     ├── Não
     └── Sim → Adicionar fotos
                  ↓
             Criar anúncio
                  ↓
          Definir status inicial
                  ↓
             Confirmar
                  ↓
                 Fim
```

## Fotos são opcionais

No modelo de dados:

```text
ANÚNCIO 1 ─── 0..N FOTO_ANUNCIO
```

Portanto, o anúncio pode existir sem fotos.

```text
Adicionar fotos?
    /        Não      Sim
   │        │
   │    Adicionar fotos
   │        │
   └───┬────┘
       ↓
 Criar anúncio
```

# 8. DA02 — Pesquisar e filtrar anúncios

## Objetivo

Representar o processo de descoberta de anúncios:

- consulta;
- pesquisa;
- filtros;
- ordenação;
- ausência de resultados;
- refinamento.

A consulta não exige autenticação.

## Fluxo principal

```text
Início
  ↓
Acessar anúncios
  ↓
Informar pesquisa?
  ├── Não
  │
  └── Sim → Informar termo
                │
                ▼
          Aplicar filtros?
            ├── Não
            └── Sim → Selecionar filtros
                         │
                         ▼
                  Consultar anúncios
                         │
                         ▼
                  Existem resultados?
                    /                            Não          Sim
                   │             │
                   ▼             ▼
            Exibir mensagem   Exibir lista
                   │             │
                   │             ▼
                   │      Selecionar ordenação?
                   │        /                               │      Não            Sim
                   │       │               │
                   │       │         Aplicar ordenação
                   │       │               │
                   │       └───────┬───────┘
                   │               ▼
                   │       Exibir resultados
                   │               │
                   └───────┬───────┘
                           ▼
                     Refinar busca?
```

## Filtros

Podem ser combinados:

- plataforma;
- categoria;
- condição;
- completude;
- preço mínimo;
- preço máximo.

Não é necessário criar uma decisão independente para cada filtro. Utilizamos:

```text
Selecionar filtros
```

e tratamos os critérios como dados da consulta.

## Ausência de resultados

```text
Existem resultados?
        │
       Não
        ↓
Exibir mensagem
        ↓
Refinar busca?
```

## Ordenação

A ordenação só ocorre quando existem resultados.

Critérios:

- menor preço;
- maior preço;
- mais recentes.

```text
Existem resultados?
       │
      Sim
       ↓
Exibir lista
       ↓
Selecionar ordenação?
   /              Não             Sim
  │               │
  │         Aplicar ordenação
  │               │
  └───────┬───────┘
          ↓
   Exibir resultados
```

A ordenação não deve estar ligada ao caminho de ausência de resultados.

# 9. DA03 — Gerenciar anúncio

## Objetivo

Representar as operações que o proprietário pode realizar depois que o anúncio já foi criado:

- consultar seus anúncios;
- editar informações;
- gerenciar fotos;
- alterar status;
- retirar anúncio.

## Autorização

O fluxo inclui a verificação de propriedade:

```text
Selecionar anúncio
       ↓
É proprietário?
    /          Não        Sim
   │           │
   ▼           ▼
Acesso      Escolher
negado      operação
```

Regra fundamental:

> **Somente o proprietário pode alterar ou retirar seu anúncio.**

Estar autenticado não significa possuir autorização para gerenciar qualquer anúncio.

## Operações

```text
              Gerenciar anúncio
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Editar      Fotos      Status
          │          │          │
          ▼          ▼          ▼
       Validar    Atualizar   Atualizar
          │          │          │
          └──────────┴──────────┘
                     │
                     ▼
                 Continuar?
```

## Retirar anúncio

No escopo atual, retirar não significa necessariamente excluir fisicamente o registro.

O anúncio possui o status:

```text
INATIVO
```

Portanto:

```text
Retirar anúncio
       ↓
Confirmar retirada?
       ↓
Alterar status para INATIVO
```

# 10. O que não representamos nos diagramas?

Nos Diagramas de Atividades estamos descrevendo o **comportamento em nível de análise**.

Por isso, não aparecem:

```text
Controller
Service
Repository
DTO
JPA
SQL
PostgreSQL
JWT
GET /anuncios
POST /anuncios
```

O foco é:

```text
O que acontece?
Quem realiza a ação?
Qual decisão pode ocorrer?
Qual é o próximo passo?
```

Os detalhes tecnológicos serão introduzidos posteriormente.

# 13. O que aprendemos com os três diagramas?

## 13.1 Um diagrama deve representar um processo compreensível

Não é necessário colocar todas as funcionalidades em um único diagrama.

Separar:

- publicação;
- consulta;
- gerenciamento;

torna os processos mais compreensíveis.

## 13.2 Nem toda decisão precisa ser detalhada

Não precisamos representar individualmente:

```text
Selecionar plataforma?
Selecionar categoria?
Selecionar condição?
Selecionar completude?
Selecionar preço?
```

Podemos abstrair essas ações em:

```text
Selecionar filtros
```

O nível de detalhe deve ser suficiente para compreender o processo sem tornar o diagrama ilegível.

## 13.3 O diagrama deve refletir as regras do domínio

Exemplos:

```text
Somente proprietário gerencia anúncio.
```

aparece como:

```text
É proprietário?
```

E:

```text
Um anúncio pode não possuir fotos.
```

aparece como:

```text
Adicionar fotos?
```

Os diagramas não devem ser desenhados isoladamente dos demais artefatos.

# 15. Próxima etapa

Os Diagramas de Atividades representam **o fluxo do processo**, mas ainda não mostram detalhadamente como os participantes colaboram para executar cada ação.

O próximo artefato natural é o:

> **Diagrama de Sequência**

A transição pode ser entendida assim:

```text
DIAGRAMA DE ATIVIDADES
        │
        │ Como o processo acontece?
        ▼
DIAGRAMA DE SEQUÊNCIA
        │
        │ Quem interage com quem?
        │ Em qual ordem?
        ▼
ARQUITETURA DA SOLUÇÃO
        │
        │ Onde cada responsabilidade será implementada?
        ▼
PWEB I
        │
        ▼
API REST + DTO + CAMADAS + PERSISTÊNCIA
```

Como primeiro exercício, podemos transformar o **DA01 — Publicar anúncio** em um Diagrama de Sequência em nível de análise, antes de introduzir `Controller`, `Service`, `Repository` e DTOs.

---

# 16. Síntese

Os três Diagramas de Atividades representam:

```text
DA01 — PUBLICAR
Usuário → informa → sistema valida → anúncio é criado

DA02 — PESQUISAR
Usuário → pesquisa/filtra → sistema consulta → resultados são exibidos

DA03 — GERENCIAR
Usuário → seleciona anúncio → sistema autoriza → operação é executada
```

A principal função desses diagramas no projeto é **transformar requisitos estáticos em uma representação visual do comportamento esperado do sistema**, preparando a passagem da análise para os modelos de interação e, posteriormente, para a implementação.
