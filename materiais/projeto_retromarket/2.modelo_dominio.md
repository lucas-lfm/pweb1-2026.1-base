# RetroMarket — Modelo Conceitual de Domínio

## 1. Contextualização

A elaboração do modelo de domínio é uma etapa de análise que busca representar os **principais conceitos do negócio e os relacionamentos existentes entre eles**.

No projeto RetroMarket, o modelo é construído a partir da análise dos requisitos funcionais, requisitos não funcionais, regras de negócio e histórias de usuário já levantados para a plataforma de anúncios de videogames retrô.

A finalidade não é definir ainda tabelas de banco de dados, classes de programação ou detalhes de implementação. O objetivo é responder, em nível conceitual:

- quais são os principais conceitos envolvidos no problema;
- quais informações caracterizam esses conceitos;
- como esses conceitos se relacionam;
- quais classificações e regras próprias do domínio precisam ser representadas.

O material de referência utilizado como modelo de organização apresenta justamente essa abordagem: partir dos requisitos e casos de uso para extrair os principais conceitos do domínio e descrevê-los em uma tabela contendo **conceito, atributos e relacionamentos**. No exemplo, essa descrição textual antecede a representação por meio de um diagrama de classes simplificado. fileciteturn4file0

# 2. Do requisito ao modelo de domínio

O modelo de domínio não deve ser criado simplesmente identificando os substantivos existentes em um requisito. A extração dos conceitos precisa considerar o **significado desses elementos dentro do negócio**.

No RetroMarket, podemos observar, por exemplo, a história:

> Como usuário autenticado, quero publicar um anúncio de um produto retrô, para disponibilizá-lo para outros usuários da plataforma.

A partir dessa história e dos requisitos associados, identificamos conceitos como:

- Usuário;
- Anúncio;
- Plataforma;
- Categoria;
- Condição;
- Completude;
- Foto;
- Localização.

Mas nem todos esses elementos precisam se transformar em uma entidade independente.

Por exemplo:

- **Usuário** representa uma entidade do domínio;
- **Anúncio** representa a oferta publicada;
- **Plataforma** representa uma classificação/referência do produto;
- **Categoria** representa o tipo do item anunciado;
- **Condição** representa uma classificação do estado do produto;
- **Completude** representa uma classificação da composição do produto;
- **Foto** representa uma informação associada ao anúncio;
- **Localização** representa uma característica do anúncio, mas, no escopo atual, pode ser tratada como atributo do anúncio.

Esse processo é importante porque evita transformar automaticamente cada informação encontrada nos requisitos em uma entidade ou classe.

# 3. Critérios utilizados para identificar os conceitos

Para construir o modelo, foram utilizadas as seguintes perguntas:

### 3.1 O conceito possui identidade própria no domínio?

Se o elemento precisa ser distinguido e referenciado independentemente, há indícios de que seja um conceito relevante.

Exemplo:

> Um anúncio precisa ser identificado para ser consultado, editado, excluído ou favoritado.

Portanto, **Anúncio** é um conceito central.

---

### 3.2 O conceito possui informações próprias?

Um conceito que possui características próprias relevantes para o negócio tende a merecer representação própria.

Exemplo:

> Plataforma possui nome, fabricante e geração.

Por isso, **Plataforma** é representada como um conceito independente.

---

### 3.3 O conceito possui relacionamento significativo com outros conceitos?

Os requisitos estabelecem relações importantes, como:

- um usuário publica anúncios;
- um anúncio pertence a uma plataforma;
- um anúncio pertence a uma categoria;
- um anúncio possui fotos;
- um usuário pode favoritar anúncios.

Esses relacionamentos ajudam a estruturar o modelo conceitual.

---

### 3.4 O elemento é realmente um conceito ou apenas uma classificação?

Esse critério é particularmente importante no RetroMarket.

**Condição**, por exemplo, possui valores definidos:

- Novo (Lacrado);
- Seminovo (Excelente);
- Usado (Bom estado);
- Recondicionado;
- Com Defeito / Sucata.

Ela é importante para o domínio, mas não precisa ser modelada como uma entidade independente.

O mesmo ocorre com:

- Completude;
- Status do anúncio.

Esses elementos podem ser representados como **classificações do domínio**.

# 4. Descrição textual do modelo de domínio

A estrutura abaixo segue a organização do material de referência: **CONCEITO, ATRIBUTOS e RELACIONAMENTOS**. fileciteturn4file0

## 4.1 Usuário

| Conceito | Atributos | Relacionamentos |
|---|---|---|
| **Usuário** | • Nome<br>• E-mail<br>• Data de cadastro | • **Anúncio:** um usuário pode publicar vários anúncios, inclusive nenhum.<br>• **Favorito:** um usuário pode possuir vários favoritos, inclusive nenhum. |

### Justificativa

O conceito **Usuário** aparece diretamente nos requisitos de cadastro, autenticação, publicação e gerenciamento de anúncios.

O usuário é também responsável por seus próprios anúncios, o que está relacionado à regra de que somente o proprietário pode alterar ou excluir um anúncio.

---

## 4.2 Anúncio

| Conceito | Atributos | Relacionamentos |
|---|---|---|
| **Anúncio** | • Título<br>• Descrição<br>• Preço<br>• Localização<br>• Data de publicação<br>• Data de atualização<br>• Condição<br>• Completude<br>• Status | • **Usuário:** um anúncio pertence a um usuário.<br>• **Plataforma:** um anúncio pertence a uma plataforma.<br>• **Categoria:** um anúncio pertence a uma categoria.<br>• **Foto:** um anúncio pode possuir várias fotos.<br>• **Favorito:** um anúncio pode ser favoritado por vários usuários. |

### Justificativa

**Anúncio** é o conceito central do RetroMarket.

As principais funcionalidades do sistema estão relacionadas à criação, consulta, alteração, pesquisa, filtragem e gerenciamento de anúncios.

---

## 4.3 Plataforma

| Conceito | Atributos | Relacionamentos |
|---|---|---|
| **Plataforma** | • Nome<br>• Fabricante<br>• Geração | • **Anúncio:** uma plataforma pode estar associada a vários anúncios. |

### Exemplos

- Super Nintendo;
- Nintendo 64;
- PlayStation;
- PlayStation 2;
- Mega Drive;
- Game Boy.

### Justificativa

Plataforma é um conceito relevante porque o domínio de retrogames exige identificar o sistema ao qual o produto está relacionado e porque os requisitos incluem pesquisa e filtragem por plataforma.

---

## 4.4 Categoria

| Conceito | Atributos | Relacionamentos |
|---|---|---|
| **Categoria** | • Nome | • **Anúncio:** uma categoria pode classificar vários anúncios. |

### Categorias definidas

- Console;
- Jogo;
- Acessório;
- Colecionável;
- Kit / Bundle.

### Justificativa

Categoria é necessária para classificar os anúncios e possibilitar a pesquisa e filtragem por tipo de item.

---

## 4.5 Foto

| Conceito | Atributos | Relacionamentos |
|---|---|---|
| **Foto** | • URL<br>• Ordem<br>• Indicador de foto principal | • **Anúncio:** uma foto pertence a um anúncio. |

### Justificativa

O requisito de cadastro de fotos estabelece que um anúncio pode possuir várias imagens. Além disso, uma imagem pode ser definida como principal.

A foto, portanto, possui informações próprias relacionadas à apresentação do anúncio.

---

## 4.6 Favorito

| Conceito | Atributos | Relacionamentos |
|---|---|---|
| **Favorito** | • Data | • **Usuário:** um usuário pode possuir vários favoritos.<br>• **Anúncio:** cada favorito refere-se a um anúncio. |

### Justificativa

Os requisitos estabelecem uma relação entre usuários e anúncios:

> um usuário pode favoritar vários anúncios e um anúncio pode ser favoritado por vários usuários.

Como essa relação possui uma informação própria — a data em que o favorito foi criado — ela é representada conceitualmente por **Favorito**.

Assim:

```text
Usuário 1 ─── N Favorito N ─── 1 Anúncio
```

representa uma relação conceitual N:N entre Usuário e Anúncio.

# 5. Classificações do domínio

Nem todo conceito importante precisa ser representado como uma entidade independente.

No RetroMarket, existem três classificações diretamente relacionadas ao anúncio.

## 5.1 Condição

Representa o estado físico/comercial do produto.

Valores:

- **Novo (Lacrado)**
- **Seminovo (Excelente)**
- **Usado (Bom estado)**
- **Recondicionado**
- **Com Defeito / Sucata**

---

## 5.2 Completude

Representa o quanto do conjunto acompanha o item.

Valores:

- **Completo (CIB)**
- **Loose (Avulso)**
- **Incompleto / Personalizado**

A distinção entre condição e completude é importante para o domínio.

Exemplo:

> Um jogo pode estar em excelente estado de conservação, mas ser vendido loose.

Portanto:

```text
Condição ≠ Completude
```

---

## 5.3 Status do anúncio

Representa a situação atual da oferta.

Valores:

- **Ativo**
- **Reservado**
- **Vendido**
- **Inativo**

O status pertence ao anúncio porque representa a situação daquela oferta específica.

---

# 6. Do modelo de domínio para o diagrama de classes conceitual

O modelo textual fornece a base para a representação gráfica.

O próximo artefato é o **diagrama de classes a nível conceitual**, no qual os conceitos identificados serão representados visualmente como classes, juntamente com:

- atributos conceituais;
- associações;
- multiplicidades;
- eventualmente generalizações, caso o domínio venha a exigir;
- classificações/enums relevantes.

Neste nível, não devem ser introduzidos elementos específicos de implementação como:

- Controllers;
- Services;
- Repositories;
- DTOs;
- frameworks;
- endpoints;
- tabelas;
- chaves estrangeiras;
- tipos específicos de banco de dados.

O diagrama deve continuar representando o **domínio do problema**, e não a solução tecnológica.

# 7. O que acontece depois do modelo conceitual?

O modelo conceitual será utilizado como entrada para as próximas etapas de modelagem.

A sequência do projeto pode ser representada assim:

```text
Requisitos
    │
    ▼
Histórias de usuário
    │
    ▼
Casos de uso
    │
    ▼
Modelo conceitual de domínio
    │
    ▼
Diagrama de classes conceitual
    │
    ▼
Modelo de dados / ER lógico
    │
    ▼
Arquitetura da aplicação
    │
    ▼
Diagramas de sequência
    │
    ▼
API REST
    │
    ▼
Implementação
```

O ponto importante é que **cada etapa acrescenta um nível de detalhamento**, sem perder a rastreabilidade com os requisitos originais.
