# RetroMarket — Contratos da API REST

## 1. Objetivo

Este documento define os contratos iniciais da API REST do **RetroMarket**, plataforma de anúncios de videogames retrô.

Os contratos foram derivados dos requisitos, casos de uso, modelo de domínio, diagramas de atividades, diagramas de sequência e arquitetura em camadas definidos para o projeto.

O objetivo é fornecer uma especificação suficientemente clara para orientar a implementação em PWEB I, sem acoplar o contrato a uma implementação específica de framework.

---

## 2. Princípios da API

A API deverá:

- utilizar HTTP;
- representar recursos do domínio por meio de URLs;
- utilizar JSON nas requisições e respostas;
- utilizar métodos HTTP coerentes com as operações;
- utilizar códigos de status HTTP adequados;
- não expor diretamente detalhes de persistência;
- utilizar DTOs como contratos de entrada e saída;
- exigir autenticação nas operações que dependem da identidade do usuário;
- aplicar autorização nas operações que modificam recursos pertencentes ao usuário.

### Prefixo

```text
/api
```

Exemplo:

```http
POST /api/anuncios
```

| Recurso | Responsabilidade |

# 4. Autenticação

## 4.1 Login

### `POST /api/auth/login`

Autentica um usuário utilizando e-mail e senha.

### Requisição

```json
{
  "email": "usuario@example.com",
  "senha": "senha-do-usuario"
}
```

### Resposta — `200 OK`

```json
{
  "token": "token-de-autenticacao",
  "tipo": "Bearer",
  "usuario": {
    "id": "uuid",
    "nome": "Nome do usuário",
    "email": "usuario@example.com"
  }
}
```

### Possíveis respostas

| Status | Situação |
|---|---|
| `200 OK` | Credenciais válidas |
| `400 Bad Request` | Dados inválidos |
| `401 Unauthorized` | Credenciais inválidas |

O mecanismo concreto de geração do token será definido na implementação.

# 5. Anúncios

O recurso `/anuncios` constitui o núcleo funcional do RetroMarket.

## 5.1 Publicar anúncio

### `POST /api/anuncios`

Cria um novo anúncio.

**Autenticação:** obrigatória.

O usuário autenticado será considerado o proprietário do anúncio.

### Request DTO — `AnuncioRequest`

```json
{
  "titulo": "Nintendo 64 completo",
  "descricao": "Console em ótimo estado de conservação.",
  "preco": 900.00,
  "plataformaId": 2,
  "categoriaId": 1,
  "condicao": "USADO_BOM_ESTADO",
  "completude": "COMPLETO_CIB",
  "localizacao": "Tauá-CE"
}
```

### Campos

| Campo | Obrigatório | Descrição |
|---|---:|---|
| `titulo` | Sim | Título do anúncio |
| `descricao` | Sim | Descrição do item |
| `preco` | Sim | Preço anunciado |
| `plataformaId` | Sim | Plataforma do item |
| `categoriaId` | Sim | Categoria do item |
| `condicao` | Sim | Estado de conservação |
| `completude` | Sim | Grau de completude |
| `localizacao` | Sim | Localização informada |

### `condicao`

```text
NOVO_LACRADO
SEMINOVO_EXCELENTE
USADO_BOM_ESTADO
RECONDICIONADO
COM_DEFEITO_SUCATA
```

### `completude`

```text
COMPLETO_CIB
LOOSE_AVULSO
INCOMPLETO_PERSONALIZADO
```

O status inicial é definido pelo sistema como:

```text
ATIVO
```

O identificador do proprietário não é enviado pelo cliente; ele é obtido a partir da autenticação.

### Resposta — `201 Created`

```json
{
  "id": "uuid",
  "titulo": "Nintendo 64 completo",
  "descricao": "Console em ótimo estado de conservação.",
  "preco": 900.00,
  "condicao": "USADO_BOM_ESTADO",
  "completude": "COMPLETO_CIB",
  "status": "ATIVO",
  "localizacao": "Tauá-CE",
  "dataPublicacao": "2026-08-09T10:30:00",
  "dataAtualizacao": "2026-08-09T10:30:00",
  "visualizacoes": 0,
  "plataforma": {
    "id": 2,
    "nome": "Nintendo 64",
    "fabricante": "Nintendo",
    "geracao": "5"
  },
  "categoria": {
    "id": 1,
    "nome": "Console"
  },
  "fotos": []
}
```

### Possíveis respostas

| Status | Situação |
|---|---|
| `201 Created` | Anúncio criado |
| `400 Bad Request` | Dados inválidos |
| `401 Unauthorized` | Usuário não autenticado |
| `404 Not Found` | Plataforma ou categoria inexistente |

# 6. Consultar anúncios

## 6.1 Listar anúncios

### `GET /api/anuncios`

Retorna anúncios disponíveis para consulta.

A operação pode ser realizada sem autenticação.

### Parâmetros

| Parâmetro | Descrição |
|---|---|
| `q` | Termo de pesquisa |
| `plataformaId` | Filtra por plataforma |
| `categoriaId` | Filtra por categoria |
| `condicao` | Filtra por condição |
| `completude` | Filtra por completude |
| `precoMin` | Preço mínimo |
| `precoMax` | Preço máximo |
| `ordenacao` | Critério de ordenação |
| `pagina` | Página |
| `tamanho` | Itens por página |

### Exemplo

```http
GET /api/anuncios?q=nintendo&plataformaId=2&precoMax=1000&ordenacao=PRECO_ASC
```

### Ordenações

```text
PRECO_ASC
PRECO_DESC
MAIS_RECENTES
```

### Resposta — `200 OK`

```json
{
  "conteudo": [
    {
      "id": "uuid",
      "titulo": "Nintendo 64 completo",
      "preco": 900.00,
      "condicao": "USADO_BOM_ESTADO",
      "completude": "COMPLETO_CIB",
      "status": "ATIVO",
      "localizacao": "Tauá-CE",
      "plataforma": {
        "id": 2,
        "nome": "Nintendo 64"
      },
      "categoria": {
        "id": 1,
        "nome": "Console"
      },
      "fotoPrincipal": {
        "url": "https://..."
      }
    }
  ],
  "pagina": 0,
  "tamanho": 20,
  "totalElementos": 1,
  "totalPaginas": 1
}
```

Quando não houver resultados, continua sendo `200 OK`:

```json
{
  "conteudo": [],
  "pagina": 0,
  "tamanho": 20,
  "totalElementos": 0,
  "totalPaginas": 0
}
```

A ausência de resultados não representa erro da API.

# 8. Alterar anúncio

### `PUT /api/anuncios/{id}`

Atualiza os dados de um anúncio.

**Autenticação:** obrigatória.

**Autorização:** somente o proprietário.

### Requisição

```json
{
  "titulo": "Nintendo 64 completo — revisado",
  "descricao": "Console revisado e funcionando perfeitamente.",
  "preco": 950.00,
  "plataformaId": 2,
  "categoriaId": 1,
  "condicao": "USADO_BOM_ESTADO",
  "completude": "COMPLETO_CIB",
  "localizacao": "Tauá-CE"
}
```

### Resposta

```http
200 OK
```

com o anúncio atualizado.

### Possíveis respostas

| Status | Situação |
|---|---|
| `200 OK` | Atualizado |
| `400 Bad Request` | Dados inválidos |
| `401 Unauthorized` | Não autenticado |
| `403 Forbidden` | Não é proprietário |
| `404 Not Found` | Anúncio inexistente |

---

# 9. Alterar status

### `PATCH /api/anuncios/{id}/status`

**Autenticação:** obrigatória.

**Autorização:** somente o proprietário.

### Requisição

```json
{
  "status": "RESERVADO"
}
```

### Valores

```text
ATIVO
RESERVADO
VENDIDO
INATIVO
```

Exemplo para retirar o anúncio:

```json
{
  "status": "INATIVO"
}
```

### Resposta

```http
200 OK
```

com o anúncio atualizado.

---

# 10. Exclusão física

A exclusão física do anúncio **não faz parte do fluxo principal definido para o RetroMarket**.

A retirada é representada pelo estado:

```text
INATIVO
```

Portanto, inicialmente não é necessário disponibilizar:

```http
DELETE /api/anuncios/{id}
```

# 11. Fotos

O modelo estabelece:

```text
Anúncio 1 ─── 0..N FotoAnuncio
```

Portanto, fotos são opcionais.

## 11.1 Listar fotos

### `GET /api/anuncios/{id}/fotos`

### Resposta

```json
[
  {
    "id": "uuid",
    "url": "https://...",
    "ordem": 1,
    "principal": true
  },
  {
    "id": "uuid",
    "url": "https://...",
    "ordem": 2,
    "principal": false
  }
]
```

## 11.2 Adicionar foto

### `POST /api/anuncios/{id}/fotos`

**Autenticação:** obrigatória.

**Autorização:** proprietário.

Contrato inicial:

```json
{
  "url": "https://storage.example/imagem.jpg",
  "ordem": 1,
  "principal": true
}
```

### Resposta

```http
201 Created
```

> O mecanismo definitivo de upload poderá posteriormente utilizar `multipart/form-data` e armazenamento externo. Para o primeiro contrato didático, uma URL simplifica a implementação.

## 11.3 Remover foto

### `DELETE /api/anuncios/{anuncioId}/fotos/{fotoId}`

**Autenticação:** obrigatória.

**Autorização:** proprietário.

### Resposta

```http
204 No Content
```

# 17. Tratamento de erros

A API deverá utilizar respostas padronizadas.

### Exemplo

```json
{
  "status": 400,
  "codigo": "DADOS_INVALIDOS",
  "mensagem": "Os dados informados são inválidos.",
  "erros": [
    {
      "campo": "preco",
      "mensagem": "O preço deve ser maior que zero."
    }
  ],
  "timestamp": "2026-08-09T10:30:00"
}
```

### Principais códigos

| HTTP | Uso |
|---|---|
| `400 Bad Request` | Dados/requisição inválidos |
| `401 Unauthorized` | Não autenticado ou credenciais inválidas |
| `403 Forbidden` | Sem permissão |
| `404 Not Found` | Recurso inexistente |
| `409 Conflict` | Conflito com o estado atual |
| `500 Internal Server Error` | Erro inesperado |

# 18. DTOs

Os contratos externos não devem depender diretamente das entidades internas.

### DTOs de entrada

```text
AnuncioRequest
UsuarioRequest
LoginRequest
AlterarStatusRequest
FotoAnuncioRequest
```

### DTOs de saída

```text
AnuncioResponse
AnuncioResumoResponse
UsuarioResponse
LoginResponse
FotoAnuncioResponse
FavoritoResponse
PlataformaResponse
CategoriaResponse
```

Isso permite que o modelo interno da aplicação evolua sem alterar necessariamente o contrato externo da API.

# 21. Relação com o DS03 refinado

O contrato de publicação concretiza o fluxo arquitetural definido no DS03-R:

```text
Cliente
   │
   │ POST /api/anuncios
   │ AnuncioRequest
   ▼
AnuncioController
   │
   │ publicar(request)
   ▼
AnuncioService
   │
   ├── validar dados
   ├── verificar plataforma
   ├── verificar categoria
   ├── criar anúncio
   └── persistir
   │
   ▼
AnuncioRepository
   │
   ▼
PostgreSQL
   │
   ▼
AnuncioResponse
   │
   ▼
HTTP 201 Created
```

Assim, o contrato da API é consequência dos casos de uso, das interações e da arquitetura projetada.

# 22. Escopo didático

A implementação pode ser incremental:

1. cadastro e autenticação;
2. publicação de anúncios;
3. consulta de anúncios;
4. filtros e ordenação;
5. alteração de anúncios;
6. alteração de status;
7. fotos;
8. favoritos.

Recursos mais avançados, como upload real para armazenamento externo, documentação OpenAPI/Swagger, rate limiting e mecanismos avançados de segurança, podem ser incorporados posteriormente sem alterar o núcleo do modelo.

# 23. Próxima etapa

Com os contratos definidos, o próximo passo é transformar os recursos da API em classes e componentes da aplicação:

```text
API REST
   ↓
Controller
   ↓
DTO
   ↓
Service
   ↓
Domain / Entity
   ↓
Repository
   ↓
PostgreSQL
```

A partir daqui, o projeto entra diretamente na fase de implementação de PWEB I, permitindo trabalhar de forma integrada:

- Spring Boot;
- Spring Web;
- DTOs;
- validação;
- arquitetura em camadas;
- Spring Data JPA;
- PostgreSQL;
- autenticação e autorização;
- tratamento de exceções;
- serialização JSON.
